## Before the tables

**Execution is not measured here, because it is proven elsewhere.** For the comparison operators Weequery hands
the provider byte for byte the statement a hand written `Where` produces, and the test suite asserts it on every
build by comparing the SQL. A server given identical SQL cannot run it more slowly, and that argument does not
depend on the machine it was made on. What is measured here is everything on *this* side of the wire.

**Read the allocation column.** For a library sitting in a request path it is usually the more interesting of the
two, and it is the one that does not move when the hardware does.

## Building the expression

The cost that is actually Weequery's. No database, no provider, no rows, once this hands back a predicate the
query is an ordinary `Where` and everything after it costs what a hand written lambda would have cost.

Bindings resolve through the process wide cache, so these are what a running application pays. What they cost
cold is in the next table.

**The last two rows are `Expression.Compile` on its own**, over the same predicate written two ways: the tree the
C# compiler produces, and the tree this library hands a provider. The gap between them is worth understanding,
because the obvious explanation is the wrong one.

It is **not** the null guards, and it is not node count. A guard costs about a fifth of the difference, and a
tree stripped back to the same node count as the C# compiler's still compiles far slower. What costs is a
different *kind* of node: every caller-supplied value is read out of a small holder object rather than written in
as a literal, because that is what makes EF Core turn it into a query parameter instead of baking it into the
SQL, one query plan per filter shape rather than one per filter value. Compiling a field read off a captured
object is markedly more expensive than compiling a constant, and that one substitution accounts for nearly the
whole gap.

So it stays wherever a provider might read it. **Where no provider will, it goes**: `BuildDelegate` writes the
values in as constants before compiling, which is why the "build and compile" row above is faster than the
"compile only" row beneath it despite also doing the building. Same predicate, same rows selected, no parameter
to preserve.

Where the compile cost lands at all is the provider's business. **EF Core caches its query plans, so it is paid
once per distinct query shape and never thought about again. `AsQueryable` over a list caches nothing and pays it
on every enumeration**, which is why this shows up so loudly in the head to head at the end of this file, and
not at all against a database.

## Declaring the allow-list

Three ways to say the same nine bindings, which do not cost the same. The fluent calls build a binding each,
every time. `BindProperties` goes through the cache and pays for a lookup and a copy. `ResolveBindables` reflects
over the type, and is the only one of the three that touches reflection at all.

**The `resolve` rows are `BindResolve`, and they are the repeat call.** What it binds, collections included, is
kept for the process under the depth, the settings and the use it was asked for, so after the first call it walks
nothing and builds nothing, and costs about what the cached request set does. The first call for each distinct
set of arguments pays the whole walk, and that is not what these measure. Settings built fresh for every call
still find the entry, being compared by what they hold, and the last row is what that comparison costs.

## A whole request

Bind, parse, build, sort, page. Nothing executes, `Build` hands back an `IQueryable` and the provider is not
asked for anything until something enumerates it, so this is the fixed cost a request pays before the database
is involved, and the number to put beside whatever the query itself takes.

## Actually filtering

In memory rather than against a database, which would mostly measure the database.

**The first two rows are the comparison that means something.** A hand written lambda and a Weequery built
delegate, both running a predicate per element with no expression tree in the path. That is the same work, so
what separates them is Weequery's real per row overhead: the null guards it puts in that a hand written predicate
leaves out.

**The three rows using `AsQueryable` are here to show why they are not that comparison.** LINQ to Objects
compiles the expression tree every time it enumerates. The cost barely moves when the row count moves by a factor
of a hundred, and handing the provider the same expression object twice does not help, because it is not per row
work, it is `Expression.Compile`, which the table above puts at roughly a third of a millisecond. A ratio
against one of those would flatter this library rather than measure it: both sides pay the same compile, and the
difference between them vanishes into it.

So read those three as one finding, which is the argument for `BuildDelegate` over `Build` on data that is
already in memory. **Against a real provider none of it applies**, EF Core caches its query plans, and the SQL
it is handed is the same SQL either way.

Every approach in this table is checked to match the same rows before anything is timed. A hand written predicate
that quietly drops the null guard filters fewer rows and looks faster for it, and no table of timings would say
so.

## Where the per row cost goes

The table above gives one per row number. It has two things in it, and only one of them is this library's.

**Read the middle row of each group first.** A C# lambda is an ordinary method the JIT can inline into the loop
calling it. The same predicate built as an expression tree and handed to `Compile` is a `DynamicMethod`, which it
cannot. That gap belongs to .NET, not to Weequery, and any comparison without a row measuring it charges the
whole thing here. So each group runs the identical predicate three ways:

1. a **C# lambda**, the floor
2. the **same predicate as a compiled expression**, the distance from the floor is the cost of using an
   expression tree at all
3. **Weequery's**, whose distance from the middle is the only part this library is responsible for

The middle and last rows are a fair pair: both are compiled trees, and since `BuildDelegate` writes its values in
as constants rather than reading them out of the holders a provider would want, both reach their values the same
way. What is left between them is the shape of the tree, the guard, and the extra comparison an `= true` puts
in where a lambda would just read the bool.

**The three groups are the null guard**, and which one a condition falls into is decided by the property's type
rather than by anything the caller wrote. A binding guards when the accessor is a reference type, a `Nullable<>`,
or reached through either. So a `bool` or a `decimal` is never guarded, and a `string` always is, however
non-nullable it was declared. Nullable reference annotations are gone by the time a binding is built, and a
`string` that a deserializer or an outer join put a null into is a null whatever the declaration promised.

1. **value types**, nothing guards, so the guard is out of the question entirely
2. **nullable string**, everything guards, because a predicate without one throws
3. **non-nullable string**, only Weequery guards, so the last two rows differ by the guard and nothing else

Each ratio is against its own group's baseline. Comparing across groups would be comparing different predicates,
and the cheaper the predicate the larger any fixed overhead looks against it, which is worth remembering before
reading a ratio here as "what Weequery costs".

## Getting it across the wire

A condition built by a client is packed, serialized, posted, deserialized and unpacked. The alternative is the
query language, which is a string on the wire and pays a parse instead. A library offering both should be able to
say which is cheaper without guessing.

{{TransportBenchmarks}}

## Against the other libraries

Sieve, Fop and Gridify solve the same problem: a filter string arrives from a caller and has to become a query.
This is the intersection of what all four can express, a filter of three terms over three types, a sort, and a
page. Nothing outside it is here. Weequery's quantifiers, bound property operands, regular expressions,
projections and translators have no counterpart in the other three; Sieve's custom filter methods and Gridify's
compiled query cache have none in Weequery.

Each library is given the same question in its own grammar, and the four are checked to select the same rows
before anything is timed. A filter that quietly matched fewer rows would look faster for it, and no table of
timings would say so.

{{ComparisonBenchmarks}}

**The baseline is a hand written predicate, and that is what makes the rest readable.** It takes no filter
string and uses no library, and it pays exactly what the four below it pay before any of them has done anything.
Read each library as its distance from that floor rather than as an absolute figure.

**Because most of every number here is the runtime.** Everything runs over an in-memory `IQueryable`, so every
library pays `Expression.Compile` on each enumeration, which the expression table above puts at roughly a third
of a millisecond, against filtering work measured in microseconds. That cost is paid equally by all four, which
is what makes the comparison fair, and it is also most of every number in the table. It is why three of the four
sit in a narrow band around 1.00: that band is largely a ratio of compile costs, not of filtering. Only a
genuine outlier separates itself from it.

So read the band as "these are not meaningfully apart on this measurement" rather than as a ranking, and take
the per row question to the two tables above, which answer it without a compile in the way. **Against a real
provider none of this applies**, EF Core caches its query plans.

Two differences did not go into the timings, because they are not about speed:

- The filter is over `Name` rather than the nullable `Alias`. Given a row holding a null, Gridify and Fop raise
  a `NullReferenceException` where Weequery and Sieve treat it as not matching. Comparing against a filter half
  of them cannot run would measure nothing, and what Weequery's guard costs is in the table above.
- Sieve throws a handful of exceptions per run internally, caught and handled, where the other three throw
  none. A few per run rather than per operation, and it does not move the timings.
